# Agent behavior and platform-awareness design

| Field | Value |
| --- | --- |
| Status | Direction accepted; implementation incomplete |
| Target | `HAL` agent, context, tools, and interactive CLI |

## Summary

HAL must match the user's requested level of action, generate commands for the
actual host shell, and avoid material environment changes that were not explicitly
requested. These behaviors belong in the product contract, not in individual skills
or model-specific prompting.

## Motivation

A coding-focused model received the request "provide a FastAPI example" and treated
it as authorization to inspect the repository, install dependencies, create an
application, and add tests. It also generated Bash commands and examples while HAL
was using Windows PowerShell. The result worked eventually, but it changed the active
environment and repository beyond the natural meaning of the request.

Separately, diagnostic inspection of a configuration file displayed an inline API
key. Configuration and logging paths therefore need explicit redaction requirements.

## Behavioral requirements

### Match the requested action level

- **BEH-001:** Questions, explanations, reviews, and requests for examples are
  read-only by default. HAL may inspect relevant local context but must not create,
  edit, delete, install, send, publish, or otherwise mutate state unless the user
  explicitly requests that outcome.
- **BEH-002:** Requests such as "build", "create this project", "implement", "fix",
  or "update the files" authorize the smallest coherent in-scope mutations needed to
  complete the request.
- **BEH-003:** When a request is ambiguous and a material mutation would change the
  result substantially, HAL must explain the proposed action and obtain direction
  rather than infer permission.
- **BEH-004:** A model's preference to verify an example does not itself authorize
  installing packages or adding files to the current repository.

### Dependency and environment changes

- **BEH-005:** Installing, upgrading, or removing packages is a material environment
  change and requires explicit user authorization or an explicit installation task.
- **BEH-006:** When dependency installation is authorized, HAL must use the active
  interpreter/environment deliberately and update the project's dependency metadata
  when the dependency is part of the project.
- **BEH-007:** HAL must distinguish temporary experiment dependencies from project
  dependencies and state which environment was changed.
- **BEH-008:** Interactive approval rules for `pip`, `python -m pip`, platform-specific
  equivalents, and file-writing tools should be documented as optional defense in
  depth. Approvals remain user-interface friction, not a sandbox or security boundary.
- **BEH-009:** Headless mode cannot rely on an interactive confirmation prompt. A
  headless request must explicitly authorize dependency installation in its prompt or
  use a future non-interactive policy designed for that purpose.

### Runtime and shell awareness

- **PLAT-001:** Every agent receives a small runtime-context block containing the host
  operating system, selected native shell and version when available, working
  directory, and path-separator conventions.
- **PLAT-002:** Runtime context is generated by HAL; the model must not infer shell
  syntax from the provider-facing tool name `bash`.
- **PLAT-003:** On Windows PowerShell, generated commands and examples must use syntax
  supported by the selected PowerShell version. In particular, Windows PowerShell
  5.1 must not receive PowerShell 7-only operators such as `&&`.
- **PLAT-004:** User-facing run instructions must match the host shell as well as tool
  calls. A successful PowerShell implementation must not finish with Bash-only
  `curl`, continuation, redirection, or pipeline examples.
- **PLAT-005:** HAL should preserve its portable provider-facing tool contract while
  making the native-shell behavior unambiguous in the system prompt and tool schema.

### Secrets and diagnostics

- **SEC-001:** Configuration inspection, diagnostics, structured logs, error messages,
  and support output must redact API keys, tokens, passwords, authorization headers,
  cookies, and provider credentials before displaying or persisting them.
- **SEC-002:** Redaction must handle nested mappings, common credential aliases, URLs
  containing secrets, and custom provider profiles.
- **SEC-003:** Tests must use unmistakably fictional placeholders and verify that
  secret values do not survive redaction.
- **SEC-004:** Documentation should prefer environment variables or an approved
  credential store over inline credentials, even when the local config is ignored.

## Prompt and enforcement layers

No single layer is sufficient. The behavior should be reinforced through:

1. A system-prompt policy describing read-only versus mutating requests.
2. A generated runtime block naming the actual OS and shell.
3. Accurate native-shell tool descriptions and examples.
4. Optional interactive `tool_approvals` for high-impact commands and write tools.
5. Tests using models/fakes that attempt unauthorized edits or incorrect shell syntax.
6. Redaction at diagnostic/logging boundaries rather than relying on model behavior.

The system prompt guides model judgment. Approval matching provides a visible user
checkpoint. The VM or sandbox remains the actual security boundary.

## Recommended approval example

Users who want confirmation around dependency and file changes may configure:

```yaml
tool_approvals:
  - pip
  - python -m pip
  - py -m pip
  - write_file
  - edit_file
```

This example does not detect every wrapper, alias, shell chain, or indirect package
manager invocation and must not be described as a security policy.

## Acceptance criteria

1. On Windows PowerShell, an agent asked to inspect or build something receives and
   follows explicit PowerShell context.
2. "Provide a FastAPI example" returns an answer without installing packages or
   writing files unless the user explicitly asks for a project to be created.
3. "Create and test a FastAPI project" may write files and may request permission to
   install missing dependencies.
4. Project dependency installation updates dependency metadata when appropriate.
5. Windows PowerShell 5.1, PowerShell 7, Bash, and POSIX shell command examples have
   focused tests.
6. Diagnostic output cannot reveal configured provider credentials.
7. Direct `!command` and model tool calls apply configured approvals consistently.

## Non-goals

- Do not attempt to parse every possible shell command into a complete authorization
  model.
- Do not claim prompt instructions or approvals form a security sandbox.
- Do not forbid read-only inspection needed to answer a question accurately.
- Do not prevent explicitly requested agentic project creation and verification.
